5. BOUNCE AND COMPLAINT HANDLING
--------------------------------
Bounces and complaints are handled automatically, end to end, with no manual
step required to stop sending to a bad address.

How an event reaches us:

  - An SES configuration set is attached to our sending, with an event
    destination publishing Bounce, Complaint and Delivery events to an SNS
    topic.
  - That topic posts to our endpoint, POST /api/v1/notifications/webhooks/ses.
  - Every incoming payload is authenticated before it is acted on: we verify
    the SNS cryptographic signature against the AWS signing certificate
    (RSA-SHA1 or RSA-SHA256 depending on SignatureVersion), we refuse any
    SigningCertURL outside the sns.<region>.amazonaws.com domain, and we
    reject any message whose TopicArn is not our configured topic. An
    unauthenticated caller cannot suppress an address.

What we do with each event:

  - Delivery  -> the message record is marked delivered, with a timestamp.
  - Bounce, type Permanent -> the message is marked failed and the recipient
    address is added to our suppression list immediately.
  - Bounce, type Transient (for example a full mailbox) -> the message is
    marked failed with the reason recorded, but the address is NOT suppressed,
    since it is likely to become valid again.
  - Complaint -> the message is marked failed and the recipient address is
    added to the suppression list immediately, whatever the feedback type.
  - Reject -> the message is marked failed with the reason recorded.

What the suppression list does:

  - It is consulted before every single send. A suppressed address is never
    queued again, for any message type, including operational announcements
    from an administrator.
  - Each blocked attempt still leaves a visible record with the reason, so
    organisers can see that a participant was not reachable by email and can
    contact them another way.
  - Entries are unique per address and per channel, so replaying the same
    event cannot corrupt the list.
  - Removing an address from the list is a deliberate administrative action,
    available only to an administrator, and is logged.

Monitoring:

  - Every outbound message is persisted with its own status lifecycle
    (queued, sending, sent, delivered, read, failed), its attempt count and
    its failure reason.
  - Administrators have a screen listing all messages with status and reason,
    and a separate view of the suppression list, so any rise in bounces or
    complaints is visible immediately rather than discovered later.
  - Retries are capped at 5 attempts per message, after which the message is
    marked failed and abandoned rather than retried indefinitely.
  - Account-level suppression is enabled on our SES account as a second line
    of defence behind our own list.
