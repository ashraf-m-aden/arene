5. BOUNCE AND COMPLAINT HANDLING
--------------------------------
Handled automatically, with no manual step needed to stop sending to a bad
address.

How events reach us: an SES configuration set publishes Bounce, Complaint and
Delivery events to an SNS topic, which posts to our endpoint
POST /api/v1/notifications/webhooks/ses. Every payload is authenticated before
it is acted on - we verify the SNS signature against the AWS signing
certificate (RSA-SHA1 or RSA-SHA256 per SignatureVersion), refuse any
SigningCertURL outside sns.<region>.amazonaws.com, and reject any message whose
TopicArn is not our configured topic. An unauthenticated caller cannot suppress
an address.

What each event does:

  - Delivery: message marked delivered, with a timestamp.
  - Bounce, Permanent: message marked failed, recipient added to our
    suppression list immediately.
  - Bounce, Transient (a full mailbox, say): marked failed with the reason
    recorded, but NOT suppressed, as the address may become valid again.
  - Complaint: message marked failed and recipient suppressed immediately,
    whatever the feedback type.
  - Reject: marked failed with the reason recorded.

The suppression list is consulted before every single send. A suppressed
address is never queued again for any message type, operational announcements
included. Each blocked attempt still leaves a visible record with its reason,
so organisers can see a participant is unreachable by email and use another
channel. Entries are unique per address and channel, so replaying an event
cannot corrupt the list. Removing an address is a deliberate administrative
action, restricted to administrators and logged.

Monitoring: every outbound message is persisted with its status lifecycle
(queued, sending, sent, delivered, read, failed), attempt count and failure
reason. Administrators have one screen listing all messages with status and
reason, and another for the suppression list, so a rise in bounces or
complaints is visible immediately rather than discovered later. Retries are
capped at 5 attempts, after which a message is abandoned rather than retried
indefinitely. Account-level SES suppression is enabled as a second line of
defence behind our own list.
